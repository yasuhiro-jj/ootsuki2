# セキュリティ

RLS が無いことを安全とは扱わない。防御はアプリの認証と、クエリに必ず入る `organization_id`。

## 境界

1. Better Auth のセッションが無い API は 401
2. 企業 ID または slug で組織を引く
3. `memberships` を `(organization_id, user_id)` で引く。行が無ければ 404
4. `disabled` は 403、`invited` は 403、企業の `suspended` と `closed` は 403
5. 顧客とメンバーの更新は、その企業 ID と対象 ID の両方で絞る
6. 最後の有効オーナーは、トランザクション内でオーナー行をロックしてから削除・降格・停止を拒否する
7. 想定外の例外は `internal_error` だけを返す。接続文字列はログからも `postgres://` を消す
8. 顧客 JSON は 100KB を超えたら 413。Zod のエラーは項目名だけで、入力値は返さない

## 脅威

- 他社の顧客 ID を自社の URL に載せても 404。行は変わらない
- 自社の ID を他社の URL に載せても、未所属なら 404
- 顧客作成の UUID が他社の主キーと衝突したら 409。相手の顧客は返さない
- 写真キーは `org/{orgId}/visits/{visitId}/{photoId}`。他社のキーは拒否する。公開 URL は発行しない
- 位置はチェックイン時だけ、という方針。クライアントの座標は証明ではない。50m 超は警告であり拒否ではない
- スタッフは他人の訪問を編集できない、という判定はある。訪問の更新 API は未接続
- `/admin` は企業データを読まない

## まだ無いもの

行レベルセキュリティ、招待の期限、メール確認、写真の実体検査、レート制限の追加調整、監査ログの保管期限。Better Auth の初期レート制限には手を入れていない。
